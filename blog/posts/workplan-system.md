# 从一张共享 Excel 到内网周计划系统

做这个系统的起因很简单：一张周计划表，需要很多人一起填写。

以前，我们用共享 Excel 填写周计划。项目、船号、图纸编号、工作内容、预派工时和实际工时都放在表里，开始时很直观，但参与的人多了，维护就越来越费劲。多人同时编辑，内容容易被顶掉、被覆盖；来回替换文件后，又很难确认哪份才是最新版本。管理员既要收集和核对，又要处理格式和名称不一致的问题。

人员工时也不方便统计。要看某个人一周做了什么、计划投入多少时间、实际用了多少时间，往往得在多张表之间查找；月底还要逐人、逐周归集，才能汇总到专业和月份。数据虽然都在 Excel 里，人员、项目、周期和工时之间的关系却不够清晰，一处修改之后，相关汇总也不容易同步。

这让管理员很难持续掌握填报情况，后续查询、修正和维护都依赖人工反复检查。做这个系统，就是希望把这些重复工作和容易出错的环节梳理清楚。

我想保留大家熟悉的表格形式，把容易出错的协作、校验和汇总交给系统处理。于是，这张表逐步变成了一个部署在 Windows 局域网服务器上的“工作计划与工时管理”系统。

> 本文配图为功能示意图，不包含公司 Logo 和真实业务数据。文章介绍制作思路与使用场景，不包含生产数据库、账号凭据和内部项目资料。

## 一张表背后的几个问题

首先是多人填写的冲突。大家在同一个文件里操作，改错行、覆盖内容、保存版本不一致，都可能发生。即使每个人单独交一份，管理员也要花时间拼接和整理。

人员工时的统计也是一个直接痛点。管理员需要按人员、专业、周和月查看工时，还要区分预派与实际投入。共享表格可以记录数字，却需要额外整理才能形成统一口径的汇总；漏填、重复记录和后续修改，也会增加复核工作。

其次是基础资料不统一。同一张图纸可能出现不同名称，工作类别和细分类别可能不匹配，船号也可能填错。单靠人工检查，很难每次都发现。

还有一个更隐蔽的问题：周计划之间存在联系。上一周填写的“下周计划”，到了下一周就成了“本周完成情况”。如果把它们做成两份互不关联的数据，修改一边，另一边就会落后。

最后是数据维护。程序升级了，员工已经提交的记录不能丢；程序需要回滚，也不能顺带把员工后来填写的数据恢复到过去。

## 保留表格习惯 改变填写方式

员工从浏览器打开内网地址，输入工号，进入自己的填报页面。系统带出姓名、专业和周期，图纸设备目录按专业提供，减少在大表里找自己位置的操作。

页面仍然是一张表。员工可以逐项填写，也可以从 Excel 复制多行数据；系统按目标列向右、向下填入，并根据规则校验。项目、工作类别、图纸编号等使用后台目录，选定编号后自动带出名称。

这样做的目的，是让员工继续用熟悉的方法填写，同时让数据进入统一管理的记录中。输入后的草稿用于续填，正式提交后才进入汇总，避免把未完成内容当成最终计划。

## 先把月份和周期设置清楚

工时统计不能只看“第几周”。不同年度都有第1周，跨月、调休和节假日也会影响周期划分。

所以管理员先设置统计月及工作天数，再设置填报周的实际起止日期和所属统计月。当前填报周与计划起始周按“年 → 月 → 周”选择。年度下拉只显示已经设置的统计月所属年份，不提前塞入一串没有数据的年份。

![统计月份与填报周期的设置关系](images/workplan-system/calendar.svg)

*添加月度工作天数时，先选择年份和月份，再填写工作天数。*

每月标准工时按工作天数乘以8计算。实际工时与标准工时的差额保留正负值，既能看到超出的部分，也能看到尚不足的部分。周区间导出则按选定的起始周和结束周取数据，方便阶段性检查。

## 基础目录统一维护 Excel 继续使用

系统没有取消 Excel。相反，Excel 仍然是批量准备资料、整理计划和对外输出的重要工具。

管理员按照基础设置、项目、员工、细分类别、设备图纸、填报周的顺序下载模板和导入资料。模板里的选项来自已保存的后台设置：新增专业或统计月后，先保存，再下载后续模板，避免用旧选项填写新资料。

![从基础设置到填报和统计的流程](images/workplan-system/flow.svg)

*先统一基础资料和统计周期，再分人填报，最终按人员、专业和周期汇总。*

如果导入所需的专业、工作类别或统计月不存在，系统需要明确告诉管理员先补哪一类资料，而不是只显示“上传失败”。导入后还要检查载入结果，再保存后台设置。

汇总按专业分 Sheet，支持筛选和分页。导出时可以选择专业、是否包含工时，以及按周期或按人员排序。Excel 的表头和前四列冻结，左右查看时仍能知道对应的周期、人员和序号。

## 制作过程中 最费心的是业务关系

这个系统是在实际使用反馈中逐步调整的。我结合 AI 编程工具整理需求、修改程序，再通过隔离数据和实际页面验证效果。技术上采用 Python 服务、SQLite 数据存储和浏览器页面，并提供 Windows BAT 与 PowerShell 管理入口。

真正需要反复推敲的，不是把表格画出来，而是确定每一个动作应该怎样影响已有数据。

例如，一项临时工作没有预派工时，只有实际工时。这种记录可以标记为新增，但不能强迫员工事后补造计划。再回头修改更早一周时，也不能因为页面带出了下一周的内容，就把那些已经完成的临时任务重新判为“预派工时缺失”。

又例如，预派工时与目标不一致时，需要提醒员工核对；已确认的个人计划目标与管理员默认目标之间，也必须有明确的比较规则。否则，同一个数字在不同页面里可能代表不同含义。

这些细节让我认识到：把 Excel 搬到网页只是第一步。要让系统能长期使用，还得把周期关联、版本冲突、草稿与正式记录的关系处理清楚。

## 程序可以回滚 员工数据要独立保护

部署到内网之后，维护方式同样重要。管理员不应每次升级都手动敲一串命令，所以系统提供了安装、启动、停止、重启、自检、升级和恢复等入口，并把运行和部署过程写入日志。

备份分开保存程序、数据库、配置、档案和日志。完整备份按时间保留最近10份，正在使用的恢复点受到保护。

![程序回滚与业务数据保护](images/workplan-system/backup.svg)

*程序与数据分开备份；程序回滚时，当前业务数据继续保留。*

这里坚持的一条规则是：程序回滚只替换程序，当前员工计划、实际工时、草稿、历史记录和配置继续保留。回滚前检查兼容性，并使用当前业务数据的副本验证旧程序能否启动；不能把旧数据库直接覆盖回去。

这也划清了功能边界：程序回滚不等于业务数据恢复，保留10份备份也不等于已经有每日自动备份制度。真正发生数据损坏时，仍需要维护人员核对现场与备份。

## 这次制作带来的体会

对日常管理工具来说，功能越多不一定越好。更重要的是，员工能顺手填写，管理员能看清数据，出错后能知道原因，升级后还能找到原来的记录。

这套系统没有改变周计划本身要记录什么，而是把原来分散在多人协作、人工核对和文件管理中的规则逐步落实下来。Excel 继续负责它擅长的编辑和交换，网页负责个人填报、权限和校验，服务器负责统一存储与汇总。

目前它仍按内网使用场景设计。员工仅凭工号进入的方式适合受控环境，不能直接当作面向互联网的身份认证方案。后续的完善，也会继续围绕实际使用中的问题推进，而不是单纯增加菜单和按钮。

# 从一张共享 Excel 到内网周计划系统：Python + SQLite 的极简局域网工程实践

如果你的团队还在用**共享 Excel** 写周计划，下面这些场景大概率每天都在发生：

- 多人同时打开同一个文件，谁后点保存谁覆盖前面的人，找回记录全靠猜“哪个才是最终版”；
- 同一张图纸能写出三四个别名，工作类别和细分类别张冠李戴，管理员月底核对到怀疑人生；
- 上周写的“下周计划”，这周变成了“本周完成情况”，一旦改了其中一张表，另一张表的数据就永远落后一拍；
- 月底要按**人员 × 专业 × 周 × 月**统计预派工时与实际工时，只能在几十个 Sheet 里人肉 `VLOOKUP`。

为了彻底终结这种低效协作，我用 **Python + SQLite + 浏览器原生表格**，在公司 Windows 局域网服务器上搭了一套轻量级“工作计划与工时管理”系统。**没有引入重型微服务，也不强迫大家放弃熟悉的 Excel 操作习惯**——员工依然像填表格一样从 Excel 复制粘贴，底层则全部收口到关系型数据库与严格的周期状态机里。

> 本文配图来自演示环境，已避开真实业务数据。文中聚焦工程架构、数据模型与可复现的实操思路，不包含生产数据库、账号凭据和内部项目资料。

## 一、架构选型：为什么是 Python + SQLite + Windows 脚本？

在内网受控环境下做团队工具，**部署复杂度往往比功能本身更致命**。这套系统从一开始就定下了三条硬约束：

1. **零外部中间件依赖**：不需要折腾 Docker、MySQL 集群或 Node 构建链，一台普通 Windows 局域网机器拉起 Python 服务就能跑；
2. **保留表格肌肉记忆**：前端不搞花哨的表单弹窗堆砌，核心填报区依然是一张支持键盘导航与 Excel 多行粘贴的二维表；
3. **程序与数据物理隔离**：程序随时可升级、可回滚，但员工已经提交的计划、工时和草稿绝对不能丢。

整体业务与数据流向如下：

![从基础设置到填报和统计的流程](blog/images/workplan-system/flow.svg)

*先由管理员统一基础目录与统计周期，再分人独立填报与校验，最后由服务端按人员、专业和周期自动聚合导出。*

一个推荐的工程目录结构如下，把**代码、数据库、配置、备份、日志**彻底拆开，为后续的自动化运维和无损回滚打基础：

```text
workplan-server/
├── app/                  # Python Web 服务与业务逻辑（升级/回滚仅替换此目录）
├── data/
│   └── workplan.db       # SQLite 主库（开启 WAL 模式支撑局域网并发读写）
├── config/               # 端口、局域网绑定地址、环境配置
├── backups/              # 自动生成的完整备份（按时间保留最近 10 份）
├── logs/                 # 运行日志、导入诊断日志、升级/回滚审计日志
└── scripts/              # Windows BAT / PowerShell 运维入口
    ├── install.ps1
    ├── start.bat
    ├── stop.bat
    ├── healthcheck.ps1
    └── rollback.ps1
```

## 二、先定“时间轴”：为什么工时统计不能只看第几周？

很多工时系统写到一半会发现一个坑：**不同年份都有“第 1 周”，而且跨月周、法定调休、节假日会直接打乱月度标准工时**。如果直接按自然周硬算，月底一定对不上账。

因此，系统把时间轴拆成了两层强关联配置：

1. **统计月与工作天数**：先选定年份和月份，再录入该月的实际工作天数（例如 `2026年11月` 为 `22` 天，`2026年01月` 为 `20` 天）。
2. **填报周映射**：每一条“填报周”必须明确绑定**实际起止日期**与**所属统计月**。

![选择统计年月](blog/images/workplan-system/month.png)

*统计年月选择器：年度下拉框仅动态展示已配置统计月的年份，避免出现一串空年份误导操作。*

基于这层映射，月度工时核算公式非常干净：

```python
standard_hours = work_days * 8
diff_hours = actual_hours - standard_hours  # 严格保留正负号：正数为超额投入，负数为工时缺口
```

保留差额的正负值非常关键——管理员一眼就能区分“谁在加班扛活”和“谁的工时还没填满”。导出阶段则支持按**起始周 ~ 结束周**切片提取，方便做阶段性复核。

## 三、后台配置与 6 步级联模板：用“依赖顺序”消灭脏数据

如果允许管理员随意导入基础表，很快就会出现“员工所属专业不存在”或“图纸关联不到设备类别”的孤儿数据。

为此，系统后台设计了一套**带前置依赖检查的 6 步模板导入流水线**，界面把依赖关系直接写在了操作栏上：

![后台基础设置与6步级联模板导入](blog/images/workplan-system/setup.png)

*系统后台设置界面：顶部 1~6 步模板按钮按依赖顺序排列，下方可实时维护专业、员工、月度工作天数、填报周及设备图纸目录，并内置浏览器诊断与诊断中心入口。*

### 级联依赖与动态下拉校验

六个步骤的依赖关系如下：

```text
1. 基础设置模板（专业 / 工作类别 / 月度工作天数）
   ├──▶ 2. 项目模板（可独立导入）
   ├──▶ 3. 员工模板（强依赖：专业）
   ├──▶ 4. 细分类别模板（强依赖：工作类别）
   ├──▶ 5. 设备图纸模板（强依赖：专业）
   └──▶ 6. 填报周模板（强依赖：统计月）
```

这里有一个很实用的工程细节：**“先保存，再下载下一步模板”**。
当你新增了一个专业或统计月并点击右上角 `保存后台设置` 后，服务端在生成下一步的 Excel 模板时，会实时把最新的专业列表、工作类别或统计月写入 Excel 的数据验证（Data Validation）下拉框中。这样管理员拿到的永远是带最新约束的模板。

同时，导入接口**严禁返回笼统的“上传失败”**，而是做前置外键预检，精确定位缺失项：

```python
def validate_employee_import(rows, existing_majors: set[str]):
    missing = {r["major"] for r in rows if r["major"] not in existing_majors}
    if missing:
        raise ImportValidationError(
            f"请先在【1 基础设置】中补充以下专业并保存：{', '.join(sorted(missing))}"
        )
```

## 四、保留表格手感：Excel 剪贴板矩阵粘贴 + 跨周状态机

系统之所以能让一线同事无痛切换，核心在于前端填报页保留了两个极客又接地气的特性。

### 1. 监听 `paste` 事件，实现 Excel 多行多列直接粘贴

员工打开内网地址，输入工号即可带出姓名、专业、当前填报周及本专业下的图纸设备目录。填写时除了逐格下拉选择，还可以**直接在 Excel 里框选多行多列，按 `Ctrl+V` 贴进网页表格**。

实现原理是拦截表格单元格的 `paste` 事件，解析剪贴板里的 `\r\n`（行）与 `\t`（列）制表符矩阵，从当前聚焦的 `(rowIdx, colIdx)` 开始向右、向下自动扩行填充并触发规则校验：

```javascript
tableEl.addEventListener("paste", (e) => {
  const raw = e.clipboardData?.getData("text/plain");
  if (!raw || (!raw.includes("\t") && !raw.includes("\n"))) return; // 单格文本走默认粘贴

  e.preventDefault();
  const matrix = raw
    .replace(/\r\n/g, "\n")
    .replace(/\n$/, "")
    .split("\n")
    .map((line) => line.split("\t"));

  const startCell = e.target.closest("td[data-row][data-col]");
  if (!startCell) return;

  const startR = Number(startCell.dataset.row);
  const startC = Number(startCell.dataset.col);

  matrix.forEach((rowVals, rOffset) => {
    ensureRowExists(startR + rOffset);
    rowVals.forEach((val, cOffset) => {
      applyCellValueAndValidate(startR + rOffset, startC + cOffset, val.trim());
    });
  });
});
```

选定项目编号、图纸编号后，系统自动带出对应名称；输入过程先存为**草稿（Draft）**支持随时续填，只有点击**正式提交（Submitted）**后才进入统计汇总池，彻底避免半成品数据污染报表。

### 2. 跨周状态机与“临时任务”边界处理

做周计划系统最费心的不是画表格，而是处理**时间维度上的状态联动**。实际运行中会遇到几个非常刁钻的边界场景：

- **跨周继承**：第 $N$ 周填写的“下周计划”，进入第 $N+1$ 周时会自动带出为“本周完成情况”，保证计划与结果同一数据源。
- **临时插入任务（Ad-hoc）**：员工本周临时接了一项没有预派工时的任务，只填了实际工时。系统将其标记为**新增任务**，绝不强迫员工事后“补造”一份虚假的预派计划。
- **历史周回改不误伤**：当员工回头微调更早一周的数据时，系统不会因为页面同时带出了下一周的完成情况，就把已经完成的临时任务重新误判为“预派工时缺失”。
- **目标口径对齐**：当个人已确认的计划目标与管理员默认目标不一致，或预派工时与目标存在偏差时，界面会明确触发核对提示，确保同一个数字在个人端和汇总端含义一致。

### 3. SQLite 并发与 Excel 导出体验优化

- **防锁库**：局域网内大家集中在周五下午集中提交时，SQLite 务必在初始化连接时开启 `PRAGMA journal_mode=WAL;` 与合理的 `busy_timeout`，读写并发互不阻塞。
- **导出可读性**：按专业自动分 Sheet 导出 Excel，支持按周期或按人员排序、可选是否附带工时列，并且默认**冻结首行表头与前四列**（如周期、人员、序号等），横向拉动看工时和备注时不会迷失上下文。

## 五、极简运维：程序可安全回滚，员工数据零损失

内网工具最怕“升级翻车”。为了让管理员不用每次都手动敲一串命令，项目在 Windows 上直接封装了**安装、启动、停止、重启、自检、升级、恢复**的 BAT 与 PowerShell 入口，并将每一步操作写入独立日志。

![备份中心](blog/images/workplan-system/backup.png)

*备份中心：每次安装、升级或回滚前都会自动生成完整备份，按时间滚动保留最近 10 份，并锁定当前正在使用的恢复点。*

在回滚机制上，系统死守一条红线：**程序回滚 ≠ 数据回滚**。

```text
回滚请求 ──▶ 1. 复制当前 workplan.db 到临时沙箱副本
             2. 用目标旧版本程序挂载“数据副本”尝试启动 + 跑通只读自检
             3. 校验通过？
                ├── 否 ──▶ 拒绝回滚！提示版本与当前数据结构不兼容
                └── 是 ──▶ 仅替换 app/ 程序目录，保留当前 data/ 与 config/，重启服务
```

这套“**副本预检（Dry-Run）**”机制非常实用：既保证了旧版本程序不会因为数据库表结构已升级而直接崩溃，又确保员工最新提交的计划、实际工时和草稿原封不动。同时，文档也明确划清边界——保留 10 份程序级快照不替代日常的数据库异地备份，真遇磁盘或数据损坏仍需核对现场与冷备。

## 六、动手复刻 Checklist：10 分钟搭出你的内网原型

如果你想在自己的团队内网也复刻一套类似工具，可以按下面顺序直接开干：

1. **定目录与数据库**：先建好 `app / data / config / backups / logs` 五目录结构，SQLite 建表时强制开启 `WAL` 模式，把“基础字典表（专业/项目/图纸）”与“周期事实表（统计月/填报周/工时流水）”分开。
2. **先做时间轴配置**：不要硬编码周次，先做“统计月工作天数 → 填报周起止日期”两级配置，锁定 `标准工时 = 工作天数 × 8`。
3. **打通 Excel 一进一出**：导入侧按外键依赖分步校验并给出精准缺失提示；填报侧加上 `paste` 事件的 `\t` / `\n` 矩阵解析；导出侧按专业分 Sheet 并冻结前几列。
4. **加上副本预检回滚脚本**：写一个 PowerShell 升级/回滚脚本，每次动作前先打包 `app/` 与 `data/`，回滚前先拿 `workplan.db` 的副本做一次启动验证。
5. **明确内网安全边界**：凭工号直接进入的免密方式仅适用于受控局域网；若未来要暴露到公网，务必补齐统一的登录鉴权与 HTTPS 反向代理。

一个网站能发布文章，只说明“页面已经存在”；新内容可以稳定进入、被整理、被检索、被长期保存，才算开始成为内容系统。

这套网站已经有相册、Markdown 文章、置顶、搜索和自动部署。下一步不必急着增加更多页面，应该先让内容从写作到展示形成固定流程。

先把内容模型定下来

每篇文章至少应有标题、日期、摘要、封面、正文和稳定的 slug。再根据需要增加分类、标签、专题、更新时间与草稿状态。字段越少越容易坚持，但一旦确定就尽量保持一致。

分类回答“它属于哪一类”，标签负责更细的横向联系，专题则把多篇文章组织成有阅读顺序的集合。三者用途不同，不能全部堆成一排标签。

从写完到发布只保留一条路径

理想流程是：

  1. 在 blog/posts/ 新建 Markdown。
  2. 填写统一的 Front Matter。
  3. 本地预览并检查图片、链接。
  4. 提交到 GitHub。
  5. 构建脚本生成索引和文章页面。
  6. GitHub Actions 自动部署。

生成文件不应成为主要编辑对象，正文只维护一个来源。这样修改标题、摘要或正文时，不会出现列表和详情页内容不一致。

分类、专题和归档怎样做

分类宜少而稳定，例如“技术、摄影、生活、育儿”。标签可以更具体，如 Docker、HomeKit、富士、家庭影像。专题适合“从零搭建个人网站”这类连续内容，最好提供导读和上一篇、下一篇。

年份归档看似简单，却非常适合个人网站。它不替代搜索，而是让人按时间重新走一遍内容。对长期维护的网站来说，时间本身就是重要结构。

搜索不只搜标题

小型静态站可以在浏览器端加载文章索引，搜索标题、摘要、日期、分类和标签。文章增多后再考虑生成轻量全文索引。无论采用哪种方式，都应提供“没有结果”的明确反馈，并让网址参数可以保留搜索条件。

图片是最容易失控的部分

原图、网站展示图和缩略图最好分层。上传时自动生成合适尺寸，优先采用 WebP 或 AVIF，同时保留兼容格式；为图片填写有意义的替代文本，并尽可能固定宽高，减少页面加载时跳动。

远程图片方便，但长期可用性受第三方影响。真正重要的封面与家庭照片，最好放进自己控制的存储或仓库。

别忽略订阅、链接和备份

RSS 对个人网站仍然很有价值，它让读者不依赖平台算法也能获知更新。站点地图、规范链接和清晰的页面标题有助于搜索引擎理解内容。仓库之外还应定期备份原始文章和图片，避免把 GitHub 当成唯一副本。

一个更务实的迭代顺序

我会按这个顺序继续：

  1. 统一文章元数据，修复过短摘要与失效链接。
  2. 增加分类、标签与专题。
  3. 加入上一篇、下一篇和相关推荐。
  4. 输出 RSS 与站点地图。
  5. 做图片自动压缩和链接检查。
  6. 最后再考虑评论、统计等外部功能。

内容系统成熟的标志不是功能越来越多，而是新内容进入以后，会自然落到正确的位置，并且几年后依然找得到、读得顺。
